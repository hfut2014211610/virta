# Virta Phase 3 规划：使用场景层、关键图表补位与公开发布

> 状态：规划（方向已定，细节在开工前细化）· 编写：2026-11-09
> 位置：Phase 2d（`docs/plan/PHASE_2D.md`）完成、`v0.2.0` 发布之后。
> 读者：维护者与后续的实施 Agent。规则沿用 `NEXT_PHASE.md` §0（R1–R8）、R4 修订、R9（`PHASE_2C.md` §0.4）。
> 与前几期的区别：2a–2d 都是在审查出问题之后写的详细计划。Phase 3 是方向性规划：每个模块给出目标、设计要点、契约草案、验收标准和需要确认的事项，**每个模块开工前再单独细化成实施计划**（`PHASE_3x.md`）。原因是 2d 的 Agent 实测结果会影响先后顺序。

## 0. 定位

### 0.1 判断依据（2026-11-09 第五轮审查）

- **图表种类已经够用**：35 个视图加上变体，覆盖了对比、趋势、构成、分布、关系、流程、层级、计划、质量控制、表格和报告。继续扩充种类的边际价值最低，只补两个需求明确的缺口（§3）。
- **再加视觉风格的收益很小**：已经有 6 套主题、10 种配色。观感问题出在排版细节，这部分由 2d 解决。
- **最大的增量在使用场景层**：团队真正要的是"Agent 分析完，直接产出一份能发出去的东西"。目前多图带文字的日报和周报，还要靠调用方的外层脚本拼接 HTML。

### 0.2 模块与默认顺序

| 顺序 | 模块 | 一句话 | 依赖 |
|---|---|---|---|
| 3a | **`virta brief` 简报** | Markdown 中用代码块声明图表，一条命令生成离线单文件 HTML 简报和长图 PNG | 2d 完成 |
| 3b | **gauge 仪表** | 补齐管理层汇报中常见的达成率仪表 | 无 |
| 3c | **MCP Server** | 在 CLI 契约之上做一层薄封装，Agent 可以直接调用工具而不用拼命令行 | 3a 完成（brief 也要作为工具暴露） |
| 3d | **npm 公开发布** | `npm i -g virta`，加上公开项目需要的外围配套 | 2d 完成；3a、3c 可以在 3d 之前或之后 |
| 3e | **地图** | 按 `NEXT_PHASE.md` §13 重启 | 用户提供带审图号的边界数据 |
| 3f | **Agent 复测** | 用 2d 的评估集复测，与基线对比 | 每完成一个模块都跑一次 |

**调序规则**：
- 如果 2d 评估中"首次成功率"低于 70%，或者失败主要集中在参数和契约理解上，就把 3c（MCP，结构化工具调用能降低拼命令出错的概率）提前到 3a 之前。
- 如果失败主要集中在"不知道选什么图"，就在 3a 之前插入一个推荐与技能文档改进的小模块。
- 具体顺序在 2d 收尾时，根据 IMPLEMENTATION_NOTES 中记录的评估结果确定。

### 0.3 不做

- 服务端、在线编辑器、多用户协作。
- 词云、K 线、弦图等小众图表：有明确需求再做，每个单独评估。
- 多语言 UI：文案已经集中管理，等有需求时再接 i18n。
- 插件机制，也就是允许第三方注册视图：等公开发布后看社区反馈再定。

## 1. 3a · `virta brief` 简报

### 1.1 目标

一个 Markdown 文件就是一份简报：正文是普通 Markdown，图表用 ```` ```virta ```` 代码块声明。一条命令输出：

- 单文件离线 HTML：图表可交互，正文可搜索，打印不截断；
- 长图 PNG：便于发到群里，超长时自动分页；
- JSON 回执：每个图表块各有一条子回执。

可以替代调用方现有的外层拼装脚本。数据获取和定时发送仍然留在调用方，边界与 `PHASE_2A.md` §0 一致。

### 1.2 语法草案

````markdown
# 研发截止日报 · 2026-11-05

今日到期 **3** 单，已超期 **2** 单。

```virta
file: deadline.csv          # 相对 .md 文件所在目录；也可以用 @samples/…
view: gantt
title: 截止任务甘特
spec:                       # 可选，与 --spec 的结构相同，统一经过 validateSpec 校验
  options: { todayLine: true }
height: auto
```

```virta
file: deadline.csv
view: grid
derive: [{ kind: deadlineStatus, column: 结束 }]
```
````

- 代码块内容是 YAML 的一个受限子集：只支持键值、行内对象和行内数组。
  - **待定（开工前确认）**：解析器自己写，还是引入依赖。默认自己写最小子集，因为 R2 不鼓励新增依赖；或者直接改用 JSON 代码块，代价是可读性差一些。
- 文件头可选 front matter，提供 `title`、`time`（asOf/tz，所有图表块继承）、`theme`、`palette`。
- 不认识的键或不合法的值，一律按严格校验报 INVALID_SPEC，hint 中给出出错的代码块序号和行号。

### 1.3 设计要点

- **复用而不是重写**：
  - 正文渲染复用 flow-doc，因为 report 视图已经支持 Markdown；
  - 图表块复用 compose 的面板机制：统一管线、单个预构建的 compose 运行期脚本、联动关闭；
  - 静态长图复用 2a 的 PNG 分页。
- 简报 HTML 的结构是：文档流中按位置嵌入图表块，每个图表块就是一个面板。tooltip 使用 2d 的共享模块。
- 回执：`{ files, blocks: [{ index, view, ok, warnings, modelHash }], time }`。任何一个图表块失败，整体 `ok = false`，并且仍然输出其余图表块的结果，方便 Agent 只修出错的那一块。
- 版面检查（2d 的 H6）对每个图表块生效。

### 1.4 契约（ADR-0017）

新命令：

```text
virta brief <file.md> [--export html,png] [--out] [--theme] [--as-of] [--tz] [--json]
```

另外，`guide --agent` 和 SKILL.md 中增加简报的写法示例。

### 1.5 验收

- `examples/packs/delivery/` 中新增 `daily.brief.md`，覆盖 3 个以上图表块、表格、链接和 asOf，用它做端到端测试。
- HTML 离线可用（CSP 不变）；长图 PNG 分页正确；同一个 asOf 重放时输出逐字节一致。
- 加入 2d 评估集一个新任务：A13"用简报生成一份含 3 张图的周报"。

## 2. 3b · gauge 仪表

- **视图**：`gauge`。两个变体：`arc`（半圆）和 `ring`（环形）。多个指标时按网格排列。
- **数据角色**：`metric`（可选）、`value`、`target` 或 `max`（二选一），可选的 `bands`（较差线、良好线），列名别名沿用 bullet。
- **推荐规则**：只有一行或很少几行，并且每行"值 + 目标（或量程）"都齐全时才推荐 gauge；数据有多行时，bullet 仍然优先（同一份数据下 bullet 的信息密度更高）。用语料测试锁定，不得造成已有判断回退。
- **验收**：契约、适配器、渲染器、样例、语料、版面检查（error 为 0）、交互测试（悬停能出提示框）全部齐备；在 kpi 场景包中加一张 gauge 图。

## 3. 3c · MCP Server

- **形态**：`virta mcp`，通过 stdio 启动 MCP Server，不另外开端口。工具与 CLI 一一对应：`inspect`、`validate`、`render`、`compose`、`brief`、`schema`、`list`。输入是 JSON Schema，直接由 `VIEW_SPEC_SCHEMA` 和契约生成；输出就是 CLI 的回执 envelope，结构不变。
- **依赖（开工前确认）**：
  - 方案一：引入官方 SDK，需要满足 R2（发布满 7 天、写 ADR、锁精确版本），并评估对安装包体积的影响；
  - 方案二：自己实现最小的 JSON-RPC 和 MCP 消息（initialize、tools/list、tools/call）。
  - 默认倾向方案一：协议细节交给官方实现，维护成本更低。
- **安全**：只能读写调用方指定的目录，不开放任意路径；不做网络访问。
- **验收**：用 MCP Inspector 或同类工具逐个调用工具；在一个常用 Agent 中配置这个 Server，跑一遍 2d 评估集，与 CLI 方式的结果对比。

## 4. 3d · npm 公开发布

- 包名 `virta`：2026-11-07 查询时 npmjs 上未被占用，发布前再查一次。
- `release.yml` 增加 `npm publish --provenance`。发布凭据用 npm 的 trusted publishing 或 automation token，存为仓库 secret，由用户配置。
- 公开项目的配套：
  - 英文 README（简版：安装、快速上手、视图目录、Agent 接入）；
  - SECURITY.md（漏洞报告渠道）；
  - issue 和 PR 模板；
  - CODE_OF_CONDUCT（可选）。
- 画廊发布到 GitHub Pages 作为在线演示，由 CI 在打 tag 时构建并部署。
- `virta doctor` 增加可选的新版本检查（`--check-update`），查询 GitHub Releases 的最新版本。默认不联网；网络访问只发生在这个参数下，超时 3 秒，失败时只给 warn。
- 发布前再做一次 R9 全量扫描，覆盖全部历史提交的内容和提交信息。

## 6. 3f · Agent 复测

- 每完成一个模块，用同一套评估规程复测：同一个被测 Agent、同一个模型，配置记录在 IMPLEMENTATION_NOTES 中。
- 新增任务只往后追加（A13 及以后），不修改已有任务，保证和 2d 的基线可以直接比较。
- 结果用一张表记录：版本、首次成功率、最终成功率、平均重试次数、人工可发出率。
